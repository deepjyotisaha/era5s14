What the brief asked, answered

1 · Train a dense model. R1: 16 layers × width 320, 22.5M parameters (58% of them in the feed-forward layers), 50M FineWeb tokens. Validation loss 9.0792 → 4.1230.

2 · Convert it into an MoE. Each layer's feed-forward network (FFN, 1,280 neurons) was cut into 4 slices of 320 and each slice copied 8 times: 32 experts per layer in 4 families, one expert per family per token. The MoE stores 114.4M parameters but uses 22.6M per token, the dense model's work plus the routers. The conversion keeps the function: the converted model's logits matched R1's to 1.3e-14 in fp64, and its validation loss was 4.12303 against R1's 4.12303.

3 · Show it continues to train and reduces loss. Yes. R3's validation loss fell from 4.1230 to 3.7932 (-0.3299) over 50M more tokens, with no expert ever left without tokens.

How it got there: two diagnostics

The first conversion did not keep learning. Two short diagnostic rounds on the T4 found why.

version what it tested what it found
v2 the conversion, and a 450-step preview of the MoE training conversion exact, but validation loss rose 4.1230 → 4.1625; after the switch to hard expert selection the load collapsed (MaxVio 0.07 → 1.96)
v2.1 7 runs of 200 steps, each changing one thing a 10× slower router stopped the collapse (MaxVio after the switch 0.16 vs 1.96); the loss rose whenever tokens were split across clones, even with a fixed token-to-clone table (+0.0670 vs dense)
v2.2 6 runs: a smaller learning rate for the experts experts at 1/8 speed turned +0.0724 into -0.0331 against dense after 200 steps
v3 50M tokens: R2, R2s, R3 the MoE kept learning to 3.7932 (this README)

Why the experts needed to learn slower. After the split, each clone learns from about an eighth of the tokens in a batch, so its gradient is much noisier. Adam still takes full-size steps, so the clones wandered. Storing each expert's weights divided by 8 and multiplying by 8 when used leaves the model's output unchanged, and makes Adam's steps 1/8 as large for those weights.

Findings

1 · The MoE's extra parameters helped, measured against a fair control. Slowing the experts is part of the MoE's recipe, so R2s gives the dense model's FFN the same 1/8 learning speed. R3 finished below R2s by 0.0336. The two were level for the first 15M tokens (R3 − R2s at 10.0M: +0.0038); after that R3 pulled away steadily, -0.0213 by 39.8M tokens and -0.0336 at the end.

2 · But ordinary dense training finished ahead. R3 led R2 from the first evaluation until 44.8M tokens (-0.0348 at 10.0M tokens, of which the slower learning explains most: R2s had the same early lead). In the learning-rate decay (the last 20%) R2 gained 0.1635, R3 0.1232 and R2s 0.1108, and R2 finished 0.0175 ahead of R3. A likely reason, not tested: the experts were already taking 1/8-size steps, so shrinking every step at the end gave them less to gain.

3 · The router's speed decided the balance. With the router learning at full speed, switching from random to best-score expert selection sent most tokens to one clone per family (v2, v2.1). With the router 10× slower, R3's MaxVio after the switch was at most 0.157 (0.026 at the end, over 25-step windows) and no expert went a single window without tokens. The 8 clones in each family moved steadily apart (relative distance 0.011 → 0.184): they specialised.

4 · The cost. Same arithmetic per token, but R3 ran 3.1× slower than R2 (16,253 vs 50,728 tokens/s): 32 small matrix products per layer instead of 2 large ones, plus routing. Peak memory was 11,500 MiB against 6,321 MiB, because memory follows the stored parameters and their optimiser state.

5 · Two design details that the gates caught. If each family's chosen weight is rescaled to 1 on its own, the router gets no gradient (measured: 0.0e+00, against 2.2e-02 with the four weights rescaled together to sum to 4). And the conversion is exact in maths but not bit for bit: summing four 320-neuron products rounds differently from one 1,280-neuron product (2.1e-06 relative in fp32), so the gate checks in fp64.

The setup

  • Model: GPT, 16 layers × width 320, 5 heads, GELU FFN of 1,280, vocabulary 8,192 (our own byte-pair tokenizer), sequence 512.
  • Data: FineWeb sample-10BT, 100.5M training tokens in shuffled windows. R1 reads the first 50M; R2, R2s and R3 read the next 50M in the same order.
  • Training: AdamW, batch 32 × 512, learning rate 0.001, weight decay 0.1, β₂ 0.95, clip 1.0, fp16 on a T4. Warmup-stable-decay: R1 never decays; R2, R2s and R3 lower the learning rate over their last 610 of 3,051 steps.
  • MoE (R3): 4 families × 8 clones per layer, one per family per token; the four chosen scores rescaled to sum to 4; router starts at zero, runs in fp32, output scaled by 0.1 (a 10× slower router); experts at 0.125 learning speed; probabilistic expert selection for the first 100 steps, then the best score; a per-expert bias (step 0.01) for balance plus a 0.0001 per-sequence balance loss; AdamW state copied from R1.

Limitations

  • One seed per run. The final gaps (0.0175 to R2, 0.0336 to R2s) are 14× and 27× the measured run-to-run spread, so they are clear, but a second seed would make them firm.
  • One size and one budget. The lesson's MoE gains are measured at far larger scales and budgets.
  • The decay explanation is untested. Relaxing the experts' slowdown over time is the run that would test it.
  • The diagnostics ran 200 steps each; the choice of setting for v3 came from those short runs.

Why these values

The model and the optimiser settings are session 13's, which you approved reusing ("similar to last assignment"). Two things are new:

  • The schedule is warmup-stable-decay (WSD). The learning rate rises for about 200 steps, then stays flat. It is only lowered in the last 20% of R2 and R3. R1 never decays, so the conversion in v2 happens while the model can still learn quickly. Session 13's cosine schedule would have shrunk the learning rate to 10% by then.
  • Twice the data. R1 reads the first 50M tokens. R2 and R3 continue on the next 50M, so the continuations never see a repeated sentence.

Cell 4 — data: FineWeb, a tokenizer of our own, tokenised once

What this block does

Streams FineWeb (sample-10BT) from Hugging Face, trains an 8,192-token byte-pair tokenizer on the start of it, and turns the text into two flat files of token ids: 100.5M training tokens and 1M validation tokens from separate documents. Everything is saved to Drive, so this runs once (it is the slowest part of v1, roughly 10–20 minutes).

How the runs split the data

The training file is cut into windows of 513 tokens (512 inputs plus the next token as the target), and their order is shuffled once with a fixed seed. R1 reads the first 97,632 windows of that order (50M tokens). R2 and R3 both read the next 97,632, in the same order, so the control and the MoE see exactly the same new text.

What you should see

Cell 5 — the dense model (frozen after v1)

What this block does

A small GPT: token and position embeddings, 16 pre-norm blocks, a final norm, and an output layer that shares the embedding matrix. Each block is attention followed by the feed-forward network (FFN): up widens 320 → 1,280, GELU, down narrows 1,280 → 320.

Why the FFN is written this way

The FFN is the part v2 turns into experts. It is kept as its own module, block.mlp, with two plain matrices, so v2 can swap it for an MoE layer without changing any code in this cell. That matters: the cache recognises R1 by the source of this cell, and editing it would retrain R1.

The loss is computed in slices of 8,192 tokens and recomputed in the backward pass, as in session 13, so the full table of scores over the vocabulary never sits in memory at once.

class Attention(nn.Module):
    def __init__(self, mc):
        super().__init__()
        self.n_head = mc.n_head
        self.qkv = nn.Linear(mc.d, 3 * mc.d, bias=False)
        self.proj = nn.Linear(mc.d, mc.d, bias=False)
    def forward(self, x):
        B, T, C = x.shape
        q, k, v = self.qkv(x).split(C, dim=2)
        q, k, v = (t.view(B, T, self.n_head, C // self.n_head).transpose(1, 2) for t in (q, k, v))
        y = F.scaled_dot_product_attention(q, k, v, is_causal=True)
        return self.proj(y.transpose(1, 2).reshape(B, T, C))

class MLP(nn.Module):
    def __init__(self, mc):
        super().__init__()
        self.up = nn.Linear(mc.d, mc.mlp_mult * mc.d, bias=False)
        self.down = nn.Linear(mc.mlp_mult * mc.d, mc.d, bias=False)
    def forward(self, x):
        return self.down(F.gelu(self.up(x)))

class Block(nn.Module):
    def __init__(self, mc):
        super().__init__()
        self.ln1, self.attn = nn.LayerNorm(mc.d), Attention(mc)
        self.ln2, self.mlp = nn.LayerNorm(mc.d), MLP(mc)
    def forward(self, x):
        x = x + self.attn(self.ln1(x)).to(x.dtype)
        return x + self.mlp(self.ln2(x)).to(x.dtype)

def _ce_slice(h, w, y):
    logits = h @ w.t()
    if logits.dtype in (torch.float16, torch.bfloat16):
        logits = logits.float()
    return F.cross_entropy(logits, y, reduction="sum")

def chunked_ce(h, w, y, chunk):
    """Mean cross-entropy, computed slice by slice and recomputed in the backward pass."""
    h, y = h.reshape(-1, h.size(-1)), y.reshape(-1)
    total = h.new_zeros((), dtype=torch.float64 if h.dtype == torch.float64 else torch.float32)
    for i in range(0, h.size(0), chunk):
        if torch.is_grad_enabled():
            total = total + checkpoint(_ce_slice, h[i:i + chunk], w, y[i:i + chunk], use_reentrant=False)
        else:
            total = total + _ce_slice(h[i:i + chunk], w, y[i:i + chunk])
    return total / y.numel()

class GPT(nn.Module):
    def __init__(self, mc):
        super().__init__()
        self.mc = mc
        self.wte = nn.Embedding(mc.vocab, mc.d)
        self.wpe = nn.Embedding(mc.seq, mc.d)
        self.blocks = nn.ModuleList(Block(mc) for _ in range(mc.n_layer))
        self.ln_f = nn.LayerNorm(mc.d)
        self.apply(self._init)
        for b in self.blocks:        # GPT-2 style: shrink the layers that write into the stream
            for w in (b.attn.proj.weight, b.mlp.down.weight):
                nn.init.normal_(w, std=0.02 / math.sqrt(2 * mc.n_layer))

    @staticmethod
    def _init(m):
        if isinstance(m, (nn.Linear, nn.Embedding)):
            nn.init.normal_(m.weight, std=0.02)

    def hidden(self, idx):
        T = idx.size(1)
        x = self.wte(idx) + self.wpe(torch.arange(T, device=idx.device))
        for blk in self.blocks:
            x = blk(x)
        return self.ln_f(x)

    def forward(self, idx, targets, chunk=None):
        return chunked_ce(self.hidden(idx), self.wte.weight, targets, chunk or TC.loss_chunk)

    @torch.no_grad()
    def logits(self, idx):
        return self.hidden(idx) @ self.wte.weight.t()

Cell 6 — the training loop (frozen after v1)

What this block does

One function trains any model for a given number of steps and returns its history. R1 uses it now; R2 and R3 will use the same function in v3, which is why it takes a few arguments that R1 does not need yet:

argument what R1 uses what v3 will use
init nothing: random weights R1's final weights (and optimiser state)
window_start 0 the first window after R1's data
warmup, decay 200 steps up, no decay no warm-up (already warm), decay over the last 20%
extra_loss, after_step not used the MoE's small balancing loss and bias update

How it works

  • AdamW, weight decay 0.1 on the weight matrices only, gradient clipping at 1.0.
  • fp16 autocast with loss scaling on the GPU.
  • Validation loss on the same 327k held-out tokens every 2.5M training tokens.
  • Speed is measured on the GPU clock over training steps only (the first 10 steps and every validation pass are excluded). Peak memory is torch.cuda.max_memory_allocated().
  • A checkpoint is saved every 8 minutes; after a disconnect the run resumes from it.
  • At the end, the final weights, optimiser moments and loss scaler are saved as the run's final checkpoint. R1's final checkpoint is the starting point for everything in v2 and v3.

def make_opt(model, lr):
    decay = [p for n, p in model.named_parameters() if p.dim() >= 2]
    no_decay = [p for n, p in model.named_parameters() if p.dim() < 2]
    groups = [{"params": decay, "weight_decay": TC.weight_decay},
              {"params": no_decay, "weight_decay": 0.0}]
    kw = {"fused": True} if DEVICE == "cuda" else {}
    return torch.optim.AdamW(groups, lr=lr, betas=(0.9, TC.beta2), eps=1e-8, **kw)

def lr_at(step, steps, lr, warmup, decay):
    """Warmup-stable-decay: linear up over `warmup` steps, flat, then linear down to
    min_lr_frac x lr over the last `decay` steps (decay = 0 means it never comes down)."""
    if step < warmup:
        return lr * (step + 1) / warmup
    if decay and step >= steps - decay:
        t = (step - (steps - decay) + 1) / decay
        return lr * (1 - (1 - TC.min_lr_frac) * t)
    return lr

Cell 11 — the MoE layer (option E)

What this block does

Defines FamilyMoE, the layer that replaces each FFN. It holds 32 experts in 4 families of 8. Every expert is a small FFN of 320 neurons (320 → 320 → 320). For each token:

  1. The router (a 320 × 32 matrix, run in fp32, starting at zero) gives one score per expert: softmax over all 32.
  2. In each family it picks one expert. It picks the highest logit + bias, or, during the first 300 training steps, draws one at random in proportion to those values (decision D3).
  3. The four chosen scores are rescaled together so they sum to 4 (Section 4 of the plan; the per-family rule would give the router no gradient, which Cell 13 demonstrates).
  4. Each chosen expert runs on its tokens, and the four outputs are added with their weights.

Balancing (lesson Section 18)

Each expert has a bias, used only for choosing. After every step, an expert that got more than its family's average share of tokens has its bias lowered by 0.01, and a quieter one has it raised. The bias never enters the loss. A very small per-sequence balance loss (0.0001) is added as a safety net, as in DeepSeek-V3.

Why 0.01 and not the lesson's 0.001 (decision D8). When selection switches from random to "take the highest", the 8 clones in a family are still nearly identical, and almost every token goes to whichever is a hair ahead. On the laptop, a bias step of 0.001 left the load badly uneven for 200+ steps after the switch (MaxVio above 1, one dead expert); 0.01 settled it within about 40 steps on both seeds, with no loss penalty. See the plan, Section 7.4.

Why the start is exact

With the router at zero, every score is 1/32. Each family's pick then gets weight 4 × (1/32) ÷ (4/32) = 1, so the layer adds up the four slices of the old FFN, which is exactly what the dense FFN computed.

class FamilyMoE(nn.Module):
    def __init__(self, d, q, fam, clones, scale, joint=True):
        super().__init__()
        self.d, self.q, self.fam, self.clones, self.E = d, q, fam, clones, fam * clones
        self.scale, self.joint = scale, joint
        self.w_up = nn.Parameter(torch.empty(self.E, q, d))
        self.w_down = nn.Parameter(torch.empty(self.E, d, q))
        nn.init.normal_(self.w_up, std=0.02); nn.init.normal_(self.w_down, std=0.02)
        self.router = nn.Linear(d, self.E, bias=False)
        nn.init.zeros_(self.router.weight)
        self.register_buffer("bias", torch.zeros(self.E))       # choosing only, never in the loss
        self.register_buffer("counts", torch.zeros(self.E))     # tokens per expert this step
        self.probabilistic = False
        self.aux = None

    def route(self, x2):
        """x2 [N, d] -> logits [N, E], global expert id per family [N, fam], weights [N, fam]."""
        hi = torch.promote_types(x2.dtype, torch.float32)       # fp32, or fp64 in the gate
        with torch.autocast(x2.device.type, enabled=False):
            z = x2.to(hi) @ self.router.weight.to(hi).t()
        s = torch.softmax(z, dim=-1)
        key = (z + self.bias.to(hi)).view(-1, self.fam, self.clones)
        if self.training and self.probabilistic:
            p = torch.softmax(key.reshape(-1, self.clones), -1)
            pick = torch.multinomial(p, 1).view(-1, self.fam)
        else:
            pick = key.argmax(-1)
        eid = pick + torch.arange(self.fam, device=x2.device) * self.clones
        chosen = s.gather(1, eid)
        if self.joint:
            w = self.scale * chosen / chosen.sum(-1, keepdim=True)
        else:                       # the flawed rule: each family's pick divided by itself
            w = chosen / chosen
        return z, eid, w

    def forward(self, x):
        shp = x.shape
        x2 = x.reshape(-1, self.d)
        z, eid, w = self.route(x2)
        cnt = torch.bincount(eid.reshape(-1), minlength=self.E)
        if self.training:
            self.counts += cnt.to(self.counts.dtype)
        cnt_l = cnt.tolist()
        out = torch.zeros_like(x2)
        for f in range(self.fam):
            order = torch.argsort(eid[:, f])
            xs, ys, start = x2[order], [], 0
            for c in range(self.clones):
                e, n = f * self.clones + c, cnt_l[f * self.clones + c]
                if n == 0:
                    continue
                h = F.gelu(xs[start:start + n] @ self.w_up[e].t())
                ys.append(h @ self.w_down[e].t())
                start += n
            y = torch.cat(ys)
            y = y * w[order, f].unsqueeze(1).to(y.dtype)
            out = out.index_add(0, order, y.to(out.dtype))
        if self.training and len(shp) == 3:          # per-sequence balance loss (safety net)
            B, T = shp[0], shp[1]
            local = (eid - torch.arange(self.fam, device=x.device) * self.clones).view(B, T, self.fam)
            frac = F.one_hot(local, self.clones).float().mean(1)                        # [B, fam, C]
            prob = torch.softmax(z.view(B, T, self.fam, self.clones).float(), -1).mean(1)
            self.aux = (self.clones * (frac * prob).sum(-1)).mean()
        return out.view(shp)

Cell 13 — Gates: the conversion keeps the function, the router learns, balancing works

What this block does

Four checks, each of which stops the notebook if it fails:

gate question how
G1 does the MoE compute what R1 computed? fp64 on the CPU: logits must agree to 1e-10 (relative); the fp32 difference is reported as the rounding floor; on the GPU, the validation loss must match R1's
G2 does the router get a gradient? one backward pass: every layer's router gradient must be non-zero; and the flawed per-family rule must give none (zero apart from rounding), the reason for the joint rescaling
G3 does the bias balancing work? a toy layer whose router favours one expert in each family; the bias alone must bring MaxVio down
G4 are the parameter counts right? the model's own count against the formula

Why "to 1e-10" and not "exactly"

Splitting one 1,280-neuron product into four 320-neuron products adds the same numbers in a different order, and computers round after every addition. In fp64 the difference is about 1e-15; in fp32 about 1e-7. Both are rounding, not a mismatch (plan, Section 7.1).

    """FamilyMoE with switchable clone choice, for the diagnostic only.
    mode 'design' = as v2; 'fixed0' = always clone 1; 'hash' = a fixed table by token id."""
    mode, zscale, table = "design", 1.0, None

    def route(self, x2):
        hi = torch.promote_types(x2.dtype, torch.float32)
        with torch.autocast(x2.device.type, enabled=False):
            z = self.zscale * (x2.to(hi) @ self.router.weight.to(hi).t())
        s = torch.softmax(z, dim=-1)

def _hash_table():
    """Token id -> clone, per family. Greedy: frequent tokens first, each to the least-loaded
    clone, so every clone gets about 1/8 of the token *occurrences*. Families use different
    random tie-breaks, so they split the vocabulary differently."""
    freq = np.bincount(np.asarray(TRAIN[:min(len(TRAIN), 20_000_000)]), minlength=MC.vocab).astype(np.float64)
    order = np.argsort(-freq, kind="stable")
    rng = np.random.default_rng(SEED)
    tab = np.zeros((MC.vocab, XC.families), dtype=np.int64)
    for f in range(XC.families):
        load = rng.random(XC.clones) * 1e-9
        for t in order:
            c = int(np.argmin(load)); tab[t, f] = c; load[c] += freq[t]
    return torch.from_numpy(tab)

Cell 17 — v2.2 diagnostic: is the experts' learning rate too high?

Why this cell exists

The v2.1 diagnostic (plan, Section 10) found that the router being too fast causes the collapse (fixed by a 10× slower router, run D), and that the loss rises whenever tokens are split between clones. Each clone then learns from about 2,000 tokens a step instead of 16,384, so its gradient is noisier, while Adam still takes full-size steps. This cell tests whether a smaller learning rate for the experts removes the rise.

How the experts get a smaller learning rate without touching Cell 6

Each expert's weights are stored divided by a constant c and multiplied by c in the forward pass, so the model computes exactly the same thing. Adam moves every stored number by about the learning rate, so the real weights move by c × the learning rate: the experts learn c times more slowly, and nothing else changes. The copied Adam averages are rescaled to match (momentum × c, squared average × c²), so the first step is the same as it would have been, and the start is still exact.

            self.counts += cnt.to(self.counts.dtype)

        out = torch.zeros_like(x2)
        c = self.c
        for f in range(self.fam):
            order = torch.argsort(eid[:, f])
            xs, ys, start = x2[order], [], 0
            for k in range(self.clones):
                e, n = f * self.clones + k, cnt_l[f * self.clones + k]
                if n == 0:
                    continue
                h = F.gelu(xs[start:start + n] @ (c * self.w_up[e]).t())
                ys.append(h @ (c * self.w_down[e]).t())
                start += n
            y = torch.cat(ys) * w[order, f].unsqueeze(1).to(ys[0].dtype)
            out = out.index_add(0, order, y.to(out.dtype))
        if self.training and len(shp) == 3:
            B, T = shp[0], shp[1]
            local = (eid - torch.arange(self.fam, device=x.device) * self.clones).view(B, T, self.fam)
            frac = F.one_hot(local, self.clones).float().mean(1)
            prob = torch.softmax(z.view(B, T, self.fam, self.clones).float(), -1).mean(1)
            self.aux = (self.clones * (frac * prob).sum(-1)).mean()
        return out.view(shp)

How "1/8 speed" is done

The weights concerned are stored divided by 8 and multiplied by 8 when used, so the model computes exactly the same thing, but Adam's fixed-size steps move them 1/8 as far. The copied Adam averages are rescaled to match, so the first step is unchanged. A check below confirms the function is unchanged for the dense case too.
